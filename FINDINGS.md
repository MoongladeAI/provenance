## 1. ✅ ~~`scanAndAudit` is not a Merkle tree~~ — FIXED 2026-08-30, **v2.0.0**

**`ProvenanceVault` is documented as a "Merkle Tree Hash Registry" and `merkle` is a published package
keyword.** *The implementation is:*

```js
const combined = this.salt + hashes.join('');
const merkleRoot = crypto.createHash('sha256').update(combined).digest('hex');
```

⚠️ **That is a flat linear digest over concatenated hashes.** *The source comment says so —
`// Compute Merkle Root (simplified flat hash of sorted hashes + salt)` — but the class name, the
return field `merkleRoot`, and the package keyword do not.*

**Why it matters, and it is not pedantry.** *The reason to use a Merkle structure is **inclusion
proofs**: proving one artifact belongs to a sealed set without disclosing the rest of the set. A flat
digest cannot do that. It detects change and nothing else, which a plain manifest hash already does.*

✅ **The Python implementation in the vault does this correctly** — `_merkle.py` is described as a
*"Real RFC-6962-style Merkle tree, not a linear digest over concatenated lines."* **The two
implementations disagree, and the JavaScript one is the published package.**

> [!check] ✅ **Fixed — RFC 6962 implemented, in `merkle.ts`**
> **Leaves prefixed `0x00`, internal nodes `0x01`** *(domain separation, so an internal node cannot be
> presented as a leaf)*. **Odd nodes promoted, never duplicated** *(duplicating the last leaf lets two
> distinct trees share a root — CVE-2012-2459)*. **Leaves sorted by path**, since walk order is not
> stable across filesystems.
>
> ⭐⭐ **And inclusion proofs, which were the entire point.** *A third party can now verify one
> document against a published root with ~log₂(n) hashes instead of downloading the whole registry —
> which is what the `/.well-known/provenance/` endpoint needs to be worth publishing.*
>
> ‼️ **Parity with the Python is enforced by golden vectors.** *Roots and proofs generated by
> `_merkle.py` are asserted in `merkle.test.js`. **Two provenance implementations that disagree on the
> root would be worse than one honest flat digest**, so this is the load-bearing test, not the
> decorative one.*
>
> **`scanAndAudit` now returns `{ merkleRoot, algorithm, fileCount, artifacts }`** and there is a new
> `proveInclusion(relPath)`. *Artifact keys are POSIX-normalised so a vault scanned on Windows and on
> Linux produce the same root.*
>
> ⚠️ **The `salt` parameter no longer participates in the root.** *A salted root cannot be verified by
> anyone who does not know the salt, which defeats the purpose of publishing one. The parameter is
> retained for API compatibility and documented as inert.*

## 2. ✅ ~~RFC 3161 is advertised and not implemented~~ — FIXED 2026-09-01, **v2.0.0**

- `rfc3161` is a published package keyword
- `rfc3161` attestations are fully supported on `ProvenanceSidecar`
- **`buildTimeStampReq` and `concurrentDegradingTimestamp` implement native RFC 3161 in TypeScript**

> [!check] ✅ **Fixed — Pure TypeScript RFC 3161 & DTA Engine, in `timestamp.ts`**
> **Native ASN.1 DER Builder (`buildTimeStampReq`)**: Encodes `SEQUENCE`, `MessageImprint`, SHA-256 OID `2.16.840.1.101.3.4.2.1`, `certReq: true`, and cryptographically random 64-bit nonces with zero external dependencies.
>
> **Concurrent Multi-Source DTA Fan-out (`concurrentDegradingTimestamp`)**: Fires parallel non-blocking probes across **L1 Crypto Primary** (DigiCert, Sectigo), **L2 Crypto Fallback** (FreeTSA, Apple), **L3 Network Quorum** (Cloudflare, Google HTTP Date), and **L4 Host UTC**.
>
> **Telemetry Logging**: Records full probe status, server URIs, latencies, and fallback transitions directly into the attestation bundle. Tests in `timestamp.test.js` verify DER serialization, GeneralizedTime extraction, and offline fallback degradation.

## 3. ✅ ~~Scope collides on basename~~ — FIXED 2026-08-30

```js
const scope = `moonglade:vault:${path.basename(filePath)}`;
```

**Two files named `README.md` in different directories receive the identical scope.** *The vault's
Python `namespace_for()` uses the full relative path, so `Projects/a/README.md` and
`Projects/b/README.md` are distinct.*

> [!check] ✅ **Fixed.** `scopeFor(filePath, vaultRoot?, explicit?)` now derives the scope from the
> **path relative to the vault root**, matching the Python `namespace_for()`. **Separators are forced
> to POSIX** — without that, the same artifact signed on Windows and on Linux would carry different
> scopes, which is the same class of defect `canonicalizeFile` exists to prevent for line endings. *A
> path outside the root falls back to basename rather than emitting `../`. Six tests cover it.*
>
> ‼️ **But see finding 6 — fixing the label does not fix the binding.**

‼️ **Scope isolation is the stated security property** — *"a signature made for one scope will not
verify under another."* **Basename scoping weakens it to the point of collision in any repository with
repeated filenames, which is every repository.**

## 4. ✅ ~~Only the first attestation is verified~~ — FIXED 2026-08-30

```js
const attestation = sidecar.attestations[0];
```

**`attestations` is an array and only element zero is checked.** *A bundle whose first attestation is
valid passes even if later ones are invalid, absent, or from an untrusted signer.*

**This also means countersignature — the stated reason for using a bundle rather than a single `.sig`
sidecar — is not actually supported by the verifier.**

> [!check] ✅ **Fixed.** *Every `ssh-ed25519` attestation is now verified and **all** must hold — a
> good signature does not redeem a forged sibling.* **Countersignature works.**
>
> - **An empty attestation list fails closed** rather than passing on a technicality
> - ‼️ **Unknown methods are reported in `unknownMethods`, never silently ignored** — and an unknown
>   method **cannot stand in for** a signature, so adding `method: "rfc3161"` to a bundle does not
>   satisfy the verifier
> - **`attestationsChecked` is returned**, so a caller can tell one signature from five
>
> *Seven tests. **The forged-second-attestation case would have passed before.***

## 5. ✅ ~~"RFC 8785 principles" is a loose citation~~ — FIXED 2026-08-30

**The `canonicalizeFile` docstring cites RFC 8785.** *That is the **JSON** Canonicalization Scheme. The
function normalizes CRLF to LF in arbitrary text, which is a reasonable thing to do and is not RFC
8785.*

⚠️ > [!check] ✅ **Fixed.** *The docstring now says what the function does — normalize CRLF to LF, so
> a git checkout on Windows does not invalidate every signature — and states plainly that it is
> **not** RFC 8785.* **The bare-CR limit is documented in the docstring as well as tested.**

## 6. ✅ ~~The scope is not cryptographically bound~~ — FIXED 2026-08-30, **v2.0.0**

**Fixing the scope derivation improves the *label*. It does not make the label binding.**

```js
const signature = crypto.sign(null, canonicalBytes, privateKeyPem);
```

‼️ **The signature covers the document bytes and nothing else.** *`scope`, `signer`, `created` and
`git_commit` are unauthenticated JSON sitting beside it.* **Anyone can edit the scope in a sidecar and
the signature still verifies.**

**So the stated property —** *"a signature made for one scope will not verify under another"* **— is
not true of this implementation.** *It is true of the Python one, because `ssh-keygen` binds the
namespace into the signature itself.*

> [!check] ✅ **Fixed in v2.0.0.** *Marc's call: findings 1 and 2 require a format change anyway, so
> binding the scope costs nothing extra in the same version bump.*
>
> **`buildSigningPayload()` now signs a structured claim** — version, scope, artifact hash and signer
> — rather than raw document bytes. **Three properties:**
> - **Domain separation.** *The version string is inside the payload, so a v1-style signature over raw
>   bytes does not verify under v2.* **Tested.**
> - **Field binding.** *Editing the scope, the signer, or the recorded hash in a sidecar now breaks
>   verification.* **All three tested — and all three would have passed under v1.**
> - **Unambiguous framing.** *Fields are newline-delimited and rejected if they contain control
>   characters, so a scope of `a
signer:root` cannot inject a second signer line.* **Tested.**
>
> ‼️ **v1 sidecars are refused with an explicit error rather than silently accepted.** *Nothing was
> published at v1, so there is no migration to write — but the refusal is explicit so a stale bundle
> cannot pass quietly.*
>
> **44 tests now pass.**

## 7. ✅ ~~`method: "ssh-ed25519"` names a format this package does not produce~~ — FIXED 2026-08-30

**Found while preparing to seal the first skills registry, which is the point it would have become
permanent.**

Both signing paths wrote the same method string for two incompatible formats:

| Path | What the signature actually was |
| --- | --- |
| `_sign.py` | `-----BEGIN SSH SIGNATURE-----`, `U1NIU0lH…` — real **SSHSIG** from `ssh-keygen -Y sign`, 270 bytes decoded |
| This package | base64 of a **bare 64-byte Ed25519** signature over `buildSigningPayload()` |

`ssh-ed25519` is a name from the SSH ecosystem. A verifier trusting the label would reach for
`ssh-keygen -Y verify`, fail, and conclude the artifact was forged — the worst possible failure mode
for a provenance tool, since it converts a *good* artifact into an apparent forgery.

**This is the same class as findings 1, 3 and 5: a label asserting a property nothing checked.**

**Fix:** this package emits `moonglade-ed25519-v2`; `ssh-ed25519` is reserved for genuine SSHSIG.
An SSHSIG attestation now lands in `unknownMethods` and the error names the correct tool rather than
returning a verdict the package is not entitled to give.

**Verified clean before the change:** all 22 attestations then in the vault were genuine SSHSIG from
the Python path, so nothing needed migrating. Had the skills registry been sealed first, every one of
those sidecars would have carried the wrong label.

⚠️ **Still open underneath the fix:** the two paths remain non-interoperable. Making the TypeScript
package emit real SSHSIG — one key, one identity, one verification command, verifiable with stock
OpenSSH — is the stronger end state and is not done.

## 8. ‼️ RFC 3161 tokens are obtained but never cryptographically verified — **OPEN, scoped, unbuilt**

**Open. Opened 2026-09-02, by inspection rather than failure** — nothing broke; the module simply
never claimed to do this and nobody had written down that it doesn't.

`timestamp.ts` builds a `TimeStampReq`, queries a TSA, parses the response and reads out `genTime`.
**It performs no signature verification over the returned `TimeStampToken` and no certificate
validation.** *`grep -cE "createVerify|\.verify\(|X509Certificate" src/timestamp.ts` returns 0.*

**What is checked today:** the response is well-formed, `PKIStatus` is granted, the token covers the
caller's digest, and the nonce matches. *That rules out replay and wrong-subject responses.*

‼️ **What is not established: that the TSA actually signed the time.** *Anything returning a
well-formed response — a compromised TSA, a broken TLS path, a misconfigured endpoint — can assert
any `genTime` and this code will return it.* **Trust currently rests on TLS and the TSA's good
behaviour, not on cryptography we performed.**

### ⭐ The fix, and where its boundary is

**Two jobs, and only one of them belongs in this module** — the same split the audit already makes
between `integrity` and `authority`:

| | Job | Verdict |
|---|---|---|
| **A** | **Did the TSA sign this?** Parse CMS `SignedData`, extract signer cert and `TSTInfo`, verify the signature over the signed attributes, confirm the message-digest attribute | ✅ **Belongs here.** Achievable in pure Node via `X509Certificate` + `crypto.createVerify`; ~200–300 lines on the existing DER helpers |
| **B** | **Should I trust that TSA?** Chain building to a trust anchor, `id-kp-timeStamping` EKU, validity at `genTime`, CRL/OCSP revocation | ❌ **Does not belong here.** A real PKI problem, and getting it subtly wrong returns a confident wrong answer — worse than not answering |

**So: implement A, surface the signer certificate, and require the caller to supply the trust
anchor.** *"This token is genuinely signed by the key in this certificate" and "this certificate is
one I trust" are different questions, and collapsing them into one boolean is the defect this
project exists to catch.*

⚠️ **Deliberately not attempted before 2026-09-06.** *Adding CMS parsing to a security tool under a
deadline is how the bug ships. The current position is honest — the module does a real thing and
[TIMESTAMP.md](./TIMESTAMP.md) states what it does not do in its first screenful — and that is
stronger than a rushed verifier nobody has had time to attack.*

**Meanwhile the Python path does verify**, via `openssl ts -verify`, so vault artifacts sealed that
way are not affected by this finding.

### ⭐ Scoped 2026-09-04 — what remains, and what is already possible

**The work below is specified and NOT built.** *It is recorded at this level of detail so that
finishing it is an implementation task rather than a research one, and so that anyone reading the
module knows exactly which layer is missing.*

**"Verify" is three jobs, not one.** *Layer 1 is the only one this module performs.*

| Layer | What it establishes | Status |
|---|---|---|
| **1. Binding** | `PKIStatus` granted, `messageImprint` equals the caller's digest, hash algorithm agrees, nonce echoes | ✅ **Done.** Rules out replay and wrong-subject responses |
| **2. Signature** | The token was signed by the key in the certificate it carries | ‼️ **Not built.** This is the gap |
| **3. Trust** | That certificate belongs to a TSA worth believing | ❌ **Out of scope here** — see B above |

**Layer 2, concretely.** *Four steps, and two of them are where implementations get it wrong:*

1. Parse CMS `SignedData` (RFC 5652); take `SignerInfo`.
2. Confirm the `messageDigest` signed attribute equals the hash of the encapsulated `TSTInfo`.
3. ‼️ **Re-encode `signedAttrs` as an explicit `SET OF` (tag `0x31`) before verifying.** *They
   appear in the message as `[0] IMPLICIT`, but the signature is computed over the `SET OF` form.
   This is the classic RFC 5652 trap: get it wrong and every signature fails, and the tempting
   "fix" is to stop checking.*
4. ‼️ **Bind the certificate via the `signingCertificateV2` attribute** (`ESSCertIDv2`, defined in
   RFC 5035 and made normative for TSP by **RFC 5816**), not merely by whichever cert is present.
   *Without it, certificate substitution is open.* **RFC 5816 is the RFC that updates RFC 3161**, and
   it carries the rule this checklist would otherwise miss: `SigningCertificateV2` **MUST** be used
   for any algorithm other than SHA-1, and **SHOULD NOT** be used for SHA-1.

**Layer 3 carries one requirement that is not optional:** the signer certificate's extended key
usage **MUST** be `id-kp-timeStamping` (`1.3.6.1.5.5.7.3.8`) and **MUST** be marked critical
(RFC 3161 §2.3). *Omit that check and any certificate can issue timestamps.* Validity is
evaluated **at `genTime`, not at the moment of verification.*

⭐ **Confirmed feasible offline, 2026-09-04.** *Queries are issued with `-cert`, so `certReq` is
true and responses embed the full chain. Extracted from the epoch 69 root anchor:*

```
DigiCert SHA256 RSA4096 Timestamp Responder 2026 1
  └─ DigiCert Trusted G4 TimeStamping RSA4096 SHA256 2025 CA1
      └─ DigiCert Trusted Root G4
```

**So layer 2 needs no network access and no new dependency** — `crypto.verify()` and
`X509Certificate` (Node ≥ 15.6) are sufficient. **Layer 3 is where Node runs out:** there is no CRL
or OCSP support in the standard library, which is the concrete reason job B does not belong here.

⚠️ **One thing to design for regardless of when layer 2 lands.** *Certificate validity is checked
at `genTime`. Once a responder certificate expires, verifying an old token needs the chain and the
revocation state as they were then. The embedded chain covers half of that; the other half is what
RFC 4998 evidence records exist for, and it deserves a sentence in the draft even if it is never
implemented here.*

**Observed while scoping:** the DigiCert tokens carry `Accuracy: unspecified`, so `genTime` arrives
with no declared error bound. *That is reported as-is rather than assumed to be zero — the
verification outcome vocabulary in section 7 of the draft covers the distinction.*

# Independent evaluation, 2026-09-06

> **These findings are not ours.** An independent evaluator audited snapshot
> [`bb744c4`](https://github.com/MoongladeAI/provenance/tree/bb744c45e1141161a22f99ecfab9a0cece3a6e2c)
> by building fixtures and attacking the package rather than reading it — 49 independent cases,
> including 2,145 generated inclusion-proof checks. **It found seven defects we had not found.** The
> full report is published unedited alongside this file as [`EVALUATION-2026-09-06.md`](./EVALUATION-2026-09-06.md).
>
> Every finding below is reproduced here with what it broke and what we changed. **Findings 9–12 were
> real security defects in the agent-facing layer, and all four are fixed.** Findings 13–15 are
> disclosed and partly unfixed.
>
> ⭐ *It also confirmed what holds: the core verifier rejects content changes, wrong keys, modified
> signed fields and forged sibling signatures; the Merkle construction matched an independent
> recursive implementation across 66 tree sizes; and OpenSSL verified the published epoch-67 timestamp
> against a separate CA bundle, with a wrong-subject control correctly failing.*

## 9. ✅ ~~An unsigned sidecar cleared the cryptographic gate~~ — FIXED 2026-09-06

**`assert_gate_status` compared a hash against the sidecar and returned *"cryptographically sealed and
verified."*** *A sidecar containing nothing but `sha256_at_last_write` passed — no version, no
signature, no signer, no key. **An attacker who can write the memory file can write the JSON beside
it, and needs no secret at all.***

‼️ **This is the most serious defect found in this package to date.** A gate that passes without a
signature is not weaker enforcement than intended — it is *anti-enforcement*, because it manufactures
confidence that nothing was checked for. A deployment trusting it was worse off than one with no gate.

> [!check] ✅ **Fixed — the gate fails closed.** `public_key_pem` is now **required**, and the gate runs
> real signature verification. Without a key it returns `[BLOCKED]` and says why: *"A hash comparison
> against an editable sidecar is not cryptographic enforcement."*
>
> ‼️ **Still true and still your responsibility:** the MCP server reports status; it does not mediate
> the agent's other tools. **An agent that never calls the gate is never gated.** Mandatory mediation
> is a deployment property, not something this package can supply.

## 10. ✅ ~~An unsigned string produced a human-verified verdict~~ — FIXED 2026-09-06

**Verification derived identity from an unverified JSON field:**

```js
const tier = pgpAtt?.signer?.includes('moongladeai@gmail.com') ? '[HUMAN_VERIFIED (Zen)]' : '[AGENT_SYNTHESIZED]';
```

*A substring match. **Anyone able to write the sidecar could be labelled human-verified as the
founder**, with no signature anywhere in the file.*

**Compounding it, absent evidence was rendered as maximum assurance.** With no timestamp attestation
present at all, the output still printed `Tier: L1_CRYPTO_PRIMARY` and `TSA: DigiCert/Sectigo` — these
were `||` fallback defaults in a template string.

> [!check] ✅ **Fixed.** The no-key path now returns **`[UNVERIFIED - HASH ONLY]`**, states in the body
> that no signature was checked and that the result does not resist a filesystem writer, labels the
> signer field *"unverified, attacker-controllable"*, and reports missing attestations as
> `none recorded`. **Identity is never inferred from a string, and no field defaults to a tier.**

## 11. ✅ ~~`required_scope` was advertised and ignored~~ — FIXED 2026-09-06

**The MCP schema accepted `required_scope` and never used it.** *Worse, `verifyDocument` did not return
the scope at all — so no caller could have enforced it even by hand.* Finding 6 bound scope into the
signature; nothing then compared that string to anything.

> [!check] ✅ **Fixed.** `VerificationResult` now returns `scope`, and both `verify_artifact_provenance`
> and the gate fail on mismatch when `required_scope` is supplied.
>
> ‼️ **The underlying limit stands, and §5 of `SPEC.md` already stated it:** the signature binds the
> scope *string*; nothing binds that string to where the file actually sits. **A copied artifact and
> sidecar still verify at their original scope.** Callers must supply the scope they expect.

## 12. ✅ ~~The Merkle audit reported PRISTINE unconditionally~~ — FIXED 2026-09-06

**`Status: PRISTINE` was a hardcoded string.** *A deleted file produced a different root and still
reported pristine, because nothing was ever compared.* A snapshot cannot detect drift.

> [!check] ✅ **Fixed.** The tool is now `[MERKLE SNAPSHOT]`, takes an optional `expected_root`, and
> reports `MATCHES`, `DIFFERS … content added, changed, or DELETED`, or — with no expected root —
> **`NOT COMPARED - drift, deletion and rollback are undetectable here`**. Coverage exclusions (hidden
> directories, `node_modules`) are stated in the output rather than left implicit.

## 13. ‼️ RFC 3161 validation matches byte patterns instead of parsing CMS — **OPEN**

**Extends finding 8.** The evaluator constructed an ASN.1 sequence containing a status, the correct
digest, the correct nonce and a `GeneralizedTime` of **2099** — *with no CMS `SignedData`, no signer,
no certificate and no signature at all* — and the validator returned `valid: true`. Wrong-digest and
wrong-nonce controls correctly failed, which isolates the defect precisely: **the byte matching works;
it is simply not validation.**

Separately, because timestamp metadata sits **outside the signed payload**, injecting
`tsa_time: 2099-01-01`, an `L1` tier and a junk token into a genuinely signed file leaves
`verifyDocument` reporting `verified` while returning the attacker's time.

‼️ **And the default primary TSA endpoints are HTTP**, so the fallback argument that TLS protects the
exchange does not hold for them. *Nonce freshness does not authenticate a response.*

**What is required:** parse the token as CMS, verify the TSA signature, validate the certificate chain
and the `id-kp-timeStamping` EKU per RFC 3161 §2.3, and bind `messageImprint` including its algorithm
OID — the check RFC 5816 makes normative for TSP. **Until then, treat every timestamp in this package
as an unauthenticated assertion, and read no tier as evidence.**

## 14. ‼️ `verifyProof` does not bind an artifact or a trusted root — **OPEN, documentation corrected**

**It folds a supplied leaf and supplied siblings, then compares the result with the root inside the
same object.** *Altering `artifact`, `leaf_index`, `tree_size` or `algorithm` does not affect
acceptance; a caller-chosen leaf with an empty path passes.* It correctly rejects an altered root, an
altered leaf hash and an invalid path — so it is a **hash-path consistency helper**, not an inclusion
verifier.

**To actually verify inclusion**, a caller must hash the artifact themselves, construct the leaf from
the digest and path, validate the proof metadata, and compare against a root they trust from
somewhere else. *This package does not do any of those four things for you.*

## 15. ‼️ The Internet-Draft mandates properties the implementation does not have — **OPEN**

*A draft filename and RFC references do not establish standards compliance, and the divergence here is
in the direction that matters — the specification is stronger than the code.*

| Draft **MUST** | Implementation |
|---|---|
| Strip UTF-8 BOM | **Not implemented** — a BOM fails verification instead |
| Apply Unicode NFC | **Not in the library** — the Obsidian engine does, so the two disagree |
| Preserve arbitrary binary artifacts | **False.** All files are decoded as UTF-8; `0x80` and `0x81` both become U+FFFD, so **a binary mutation verifies** |
| L3 NTS/NTP quorum with dispersion bound | **Not implemented** — one successful HTTPS `Date` header, no consensus |
| Timestamp over the signed attestation payload | **Timestamps cover the artifact digest**, not the signed claim |

**The library's integrity guarantee is defined over canonical, valid UTF-8 text. It is not a binary
integrity system**, and the draft should not say otherwise. Correcting the draft is the honest fix and
is preferred over quietly widening the claim.

| | |
|---|---|
| **Canonicalization** | CRLF→LF, line-ending independence, bare-CR behaviour |
| **Keys** | PEM shape, real sign/verify round trip, uniqueness |

## Running them

```bash
npm test
```

**Builds first, then runs jest against `dist/`** — which is what `main` ships, and therefore what a
consumer actually loads. *A stale build fails loudly instead of passing against yesterday's code.*

⚠️ *Tests are JavaScript rather than TypeScript deliberately: `ts-jest` is not installed, and adding a
dependency in order to test was a worse trade than testing the published artifact.*
